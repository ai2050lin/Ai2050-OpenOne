## 0 一句话

把「36 层平铺玻璃盒」换成**竖塔**：每层是一块参数盘，每格是一个真实 tensor；
按「运行」自底向上逐层读取真实权重数值并点亮，按「下一步」单层步进。
所有颜色与数字都来自磁盘上的 safetensors，未连接时**一格都不着色**。

## 1 公开项目对照（本轮调研结论）

查 GitHub 上的 LLM 可视化项目，取四类范式作参照：

| 项目 | 核心范式 | 值得借鉴 | 不照搬的原因 |
|---|---|---|---|
| **09Catho/axon** | 逐 token 流式推送 SAE 特征 → Three.js 3d-force-graph；节点亮度=激活强度；侧栏参数滑块（temperature/top-k/top-p） | ①「运行即点亮」的实时感 ②强度直接编码为视觉量 ③参数可实时调 | 它要 GPT-2 + SAE + GPU 前向；本项目阶段目标在**参数级**，激活级属 P2 |
| **norika1207-lab/llm-neuron-atlas** | neuron-as-city：73,728 节点 / 716K 边，全层一次渲染，空间导航 | ①「整模型一次成型」的空间感 ②确定性布局 | 全层全节点在浏览器里过重；本轮先用 28–36 个层盘聚合 |
| **fbkaragoz/synapse** | 训练中流式推送张量统计；**确定性层网格**（不随机散布）+ bloom + 阈值控制 | ①确定性布局（同层永远同位置）②bloom 辉光 ③阈值 | 依赖自定义 C++/WASM 探针与训练循环，本项目从磁盘权重读 |
| **bbycroft/llm-viz** | nano-gpt 摊成 3D，**空格单步推进 / 可暂停**，每步都有真实数值 | ①**单步推进**的节奏控制 ②逐步聚焦 | 是教学式全流水线拆解（embedding→softmax），不是参数分布视图 |

**采纳的组合**：synapse 的确定性布局 + axon 的强度着色 + llm-viz 的单步推进 + neuron-atlas 的整体空间感。
**放弃的部分**：一切需要 GPU 前向或随机撒点的做法（前者超本轮范围，后者违反「布局即结论」的纪律）。

## 2 空间结构

```
                    ┌─ HUD 左上：模型 / 结构 / 步进进度 / 色带区间
                    │
        L27 ▔▔▔▔▔▔▔  ← 顶层（读数层）
         │   ◍ ◍ ◍     ← 每层 = 12 格环形参数盘
         │  ◍     ◍       每格 = 该层一个真实 tensor
         │  ◍  ║  ◍       中心立柱 = 残差流（自底向上渐变）
         │   ◍ ◍ ◍
        L0  ▔▔▔▔▔▔▔  ← 底层
                    │
                    └─ 底部控制条：▶ 运行 / 下一步 ▸ / 重置 / 精细取数 / 自转 / 速度
```

| 元素 | 编码含义 | 数据来源 |
|---|---|---|
| 层盘数量与编号 | 模型真实层数（**不硬编码 36**；实测 qwen3-1.7b = 28 层） | `conn.config.layers` + tensor 名解析 |
| 盘上格数 | 该层真实 tensor 数（qwen3 全层 11 个） | `conn.tensors` 按层聚合 |
| 格的颜色 | 该格 tensor 的 `rms = √mean(W²)`，全局 min–max 归一 | `weights/summary` 真实返回 |
| 格心亮点半径/亮度 | 同一 rms 的二次编码（**已取数才画**） | 同上 |
| 柱阵（选中层） | 柱高 = 该格真实 rms | 同上 |
| 旋转扫描环 | 当前步进层 | UI 状态（非数据） |
| 上升粒子 | 信息流方向示意（**不承载数据**） | 纯装饰 |
| 中心立柱 | 残差流示意（不承载数值） | 纯结构 |

**色带**：石板灰 `#94a3b8` → 天青 `#0ea5e9` → 靛蓝 `#6366f1` → 品红 `#d946ef` → 琥珀 `#f59e0b`。
未取数的格固定为 `#cbd5e1` 冷灰，与「已点亮」在视觉上不可混淆。

## 2.5 五种显示效果（底部「视图」下拉切换）

同一份真实数值换五种摆法，**只改呈现、不改口径**：任何视图里，未取数的格都不着色。

| 视图 | id | 摆法 | 信息侧重 | 相机预设 |
|---|---|---|---|---|
| 光塔 · 层盘环 | `tower` | 每层一圈平盘沿 Y 轴堆叠，中心残差流立柱 | 层间纵向对比（默认） | yaw .62 / pitch .30 / dist 30 |
| 螺旋梯 · 光带 | `helix` | 每层盘逐层转过 0.44 rad，相邻层外缘连成螺旋脊 | 层间推进路径、连续性 | .95 / .24 / 32 |
| 地层矩阵 · 柱阵 | `matrix` | 行 = 层（纵深），列 = tensor，柱高 = 归一化 rms | **层内分布**（唯一「高度即数值」） | .70 / .60 / 34 |
| 星核 · 同心球壳 | `orb` | 层 = 同心球壳，半径随层号递增，每壳 2–3 个大圆 | 整体感 / 由内向外展开 | 1.02 / .34 / 30 |
| 粒子星河 · 旋涡 | `nebula` | 每格一颗粒子（大小/亮度 = rms），未取数 = 暗尘 | 密度与亮度结构 | .42 / .26 / 32 |

实现要点：
- 渲染层为 `RENDER` 注册表（`{tower, helix, matrix, orb, nebula}` → `drawX(S, d)`），
  主循环只做「清屏 → 分发 → 下一帧」，切视图不重建 canvas、不重取数据。
- 五视图共用 `lvOf()` / `cellV()` 两个取值助手，杜绝「某个视图自己算了一套」。
- `LEGEND` 与 `VIEWS` 同集，图例随视图换文案（避免图例说 A、画面画 B）。
- 命中区：塔/螺旋/矩阵按盘面或行带，星核按层号，星河按「标签 + 轨道环」两段命中。
- 「地层矩阵」在快速取数下只有 3 列有值（列数 = 该层 tensor 数），提示开「精细取数」填满；
  未填的列显示冷灰平板，不补假值。

## 3 交互

| 操作 | 行为 |
|---|---|
| **▶ 运行** | 自当前层向下逐层请求 `weights/summary`，每层点亮并保留余晖；可暂停 |
| **下一步 ▸** | 单层步进（不连跑），停在该层并显示右上角读数 |
| **重置** | 清空已取数值与游标，回到未运行态 |
| **精细取数** | 关：每层 3 个承重矩阵（q/gate/down）；开：该层全部大矩阵（≤24，服务端上限） |
| 速度滑块 | 0.25×–3×（仅影响层间停留，不影响取数） |
| 左键拖拽 | 旋转（yaw/pitch） |
| 右键拖拽 | 平移 |
| 滚轮 | 缩放（dist 10–90） |
| 点击层盘 | 选中该层 → 柱阵展开 + 右侧参数表 + 下钻入口 |

## 4 数据链路（全部真实，零播种值）

```
POST /api/live/connect {model_path}
  └→ 读 config.json + safetensors 权重头（不加载权重）· 实测 0.019 s / 90 KB
     返回 tensors[]（name/shape/dtype/params/file）+ groups + config

POST /api/live/weights/summary {names:[≤24]}
  └→ 每个 tensor 取 32 块 × 64 行，超限时行域均匀抽样
     实测 qwen3-1.7b：0.20 s / 层（3 tensor）· 0.43 s/层（含 3 次开文件）
     返回 {rms, mean_abs, max_abs, min, max, sampled, rows_examined}
```

**抽样口径在界面上固定标注**：右上角读数在 `sampled=true` 时显示「抽样」徽标，
右侧说明写死「32×64 行块 / 超限均匀抽样」，不把采样值说成全量。

### 实测数值（qwen3-1.7b，28 层 × 3 probes）

| 指标 | 值 |
|---|---|
| 逐层 rms 区间 | 0.032827 – 0.037065 |
| 极差比 | 1.13× |
| 全 28 层扫描 | 11.96 s（平均 0.427 s/层） |
| 每层 probe 数 | 3 / 3（无缺失） |
| 单层读数（L0） | q_proj 0.035170 · gate_proj 0.038620（抽样）· down_proj 0.033226 |

极差仅 1.13× 说明 **bf16 权重在各层幅值高度均匀**——这本身是一个可用的观察：
层的差异不体现在权重幅值上，而在方向与组合上。这一点与项目「差分搬运不等于机制」的判断一致，
也说明**仅靠权重幅值无法区分层功能**，后续必须接激活级（P2）。

## 5 服务端缺陷修复（本轮发现并修好）

### 5.1 现象

`/api/live/weights/scan` 与 `/api/live/weights/summary` 在真实模型上：
- **单次调用正常**（0.20 s 返回）
- **连续调用必挂**：`OSError: 页面文件太小，无法完成操作 (os error 1455)`

→ 意味着「运行」按钮跑到第 2–3 层就 500，「层基线扫描」也永远跑不完。
既有 UI 的「层盒数值着色」从未在真实模型上完整跑通过。

### 5.2 根因

`safetensors.safe_open(framework='pt')` 每次调用都会 **mmap 整个权重分片**（qwen3-1.7b 单个分片 3.44 GB）。
逐层扫描是 28 × 3 = 84 次调用，映射未及时释放，累积耗尽 Windows 提交内存。

### 5.3 修法

`deploy/distributed_service.py` 的 `_wt_blocks` 改为 **safetensors header + 精确 seek 直读**：

```python
# 原：safe_open(path, framework='pt') → 整文件 mmap
# 新：
hdr, base = _wt_header(path)          # 8B 长度 + JSON header（按 size/mtime 缓存）
off0 = hdr[name]['data_offsets'][0]
f.seek(base + off0 + r0 * row_bytes)  # 只读需要的行块
raw = f.read((r1 - r0) * row_bytes)
arr = np.frombuffer(raw, np_dtype).reshape(...)   # BF16: (u16 << 16).view(f32)
torch.from_numpy(arr)                 # 零拷贝，调用方接口完全不变
```

新增 `_ST_ITEMSIZE` / `_st_np_dtype` / `_wt_header` / `_st_read_rows` 四个辅助；
`_wt_blocks` 的签名与返回类型（`(start_row, float32 tensor, sampled)`）保持不变，
因此 `_wt_scalar_stats` 与 `_wt_tensor_detail` **一行都不用改**。

> 踩坑记录：新函数最初命名为 `_st_header`，与本模块已有的 `_st_header`（供模型扫描、
> 返回 dict）同名，覆盖后导致 `/live/connect` 报 `'tuple' object has no attribute 'items'`。
> 已改名为 `_wt_header` 并在注释里写明两者区别。

### 5.4 证据（同进程 A/B）

| 路径 | 结果 |
|---|---|
| 原实现（`safe_open` mmap） | 在 84 次扫描中，**第 1 次**即 `OSError 1455` |
| 新实现（seek 直读） | **84/84 全过**，11.96 s，无异常 |
| 数值等价（内存充足时对照） | 4 个 tensor（BF16 2D ×3 + BF16 1D ×1）的 mean / mean_abs / rms / min / max / max_abs **逐项一致**（差 < 1e-6） |
| 连续 30 次直读 | 无 OSError |

验证脚本：
- `tests/gpt5_temp/_st_direct_read.py`（等价性 + 连续 30 次）
- `tests/gpt5_temp/_wt_blocks_verify.py`（28 层全量 + A/B 对照）
- `tests/gpt5_temp/_livestage_smoke.js`（前端数据链路 25 项断言）

### 5.5 为什么这不是「为通过测试而改」

- 改动只触及读取方式，不改任何统计口径（同样是 32×64 行块 + 超限抽样）
- 有逐项数值等价证明，不是「跑通就行」
- 原实现的问题在**任何** Windows 机器上、只要模型分片大于可用提交余量就会复现；
  修完后内存占用从「O(文件大小)」降到「O(一个行块)」（约 1.5 MB）

### 5.6 投影焦距标定缺陷（加多视图时发现并修）

`proj()` 原式 `f = dist*1.72/max(2,d) * (cv.height/900) * dpr()`：`cv.height` 已是设备像素，
再乘 `dpr()` 属重复计入，且 `1.72` 是把「世界单位」当「像素」用的经验常数。实测后果：

| 量 | 修前 | 修后 |
|---|---|---|
| dist=30 的焦距 | **5.35** device px / 世界单位 | **126** device px / 世界单位 |
| 28 层塔总高 | 43 device px = **22 CSS px** | 1020 device px ≈ **510 CSS px** |
| 层盘直径 | **10.8 CSS px** | **255 CSS px** |

即此前舞台上只有一个几十像素的小点——**该缺陷从未被目视发现**（视觉验收一直挂账）。
现改为 `f = cv.height * 2.7 / max(2, d)`：以 dist=30 时塔高约占 65% 画布标定，
滚轮改 `dist` 仍是等比缩放（10–90 对应约 9× 缩放范围）。
同时把格心光点半径按新尺度放大（约 2–6 device px），否则亮点在新尺度下不可见。

> 教训：几何量必须做「屏幕像素」量纲核对，不能只看代码自洽。
> 新增的 `tests/gpt5_temp/_livestage_views.js` 正是为此加了取景断言（bbox 必须落在画布内且占屏达标）。

## 7 已知限制（必须正视）

1. **只有参数级，没有激活级。** 权重是训练后的静态量，能回答「写在哪」，不能回答「何时被调用」。
   极差比 1.13× 说明幅值几乎不分层，**层的功能差异不体现在权重幅值上**——这是本视图的天花板。
   激活级（逐 token 残差流）需要加载权重到 GPU，属 P2；界面已注明，不假装有。
2. **抽样不等于全量。** 大 tensor 只读 2048 行（32×64），界面标「抽样」，但用户仍可能误读为全量统计。
   对外引用时必须带这个限定。
3. **「运行」的语义是「逐层读取」，不是模型前向。** 按钮名容易让人以为是 inference。
   已在右侧「运行说明」第 1 条写明，但这是命名上的隐患，后续可考虑改为「扫描」。
4. **布局是聚合近似。** 每层 12 格代表 11–13 个 tensor，格内不代表空间位置，只代表「该 tensor 的标量强度」。
   不能从格的角度读出任何几何含义。
5. **粒子与立柱是装饰。** 不承载数据，不能作为「信息流」的证据引用。
6. **本机实测受限。** 验证期间用户的研究任务占用 ~20 GB 工作集 / 34.78 GB 提交内存，
   服务端与浏览器都不宜再拉起，因此**仍未做浏览器端截图**。
   现状：`vite build` 零错误、`eslint` 零告警、数据链路 25 项断言 + 多视图 59 项断言全过
   （含五视图的取景 bbox 断言），但**像素级观感（透明度、重叠、标签可读性）仍需目视确认**。
   注意：多视图冒烟暴露并修掉了投影焦距缺陷（见 5.6），说明「不目视」确实有代价。
