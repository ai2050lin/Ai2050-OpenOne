01现状诊断：为什么“混乱”

混乱的根源不是界面数量多，而是没有统一的组织轴——同一批“图谱对象”被按“技术视角”“知识视角”“资产视角”切了三刀，每一刀都起了新名字，用户无法回答“我现在看的是哪一层、哪一维”。

✕二级 Tab 嵌套

「路线」下有「行业进展/图谱」两个 tab，进入图谱后又出现「图谱全景/跨线账本/结果库/模板与技术」四个 tab，两层 tab 叠加，导航深度过深。

路线 → [行业进展 | 图谱] → [图谱全景 | 账本 | 结果库 | 模板与技术] → 全景内再 [模块|模块空间|模板空间|卡片]

✕“模块 / 模块空间 / 模板空间”三概念混淆

「模块」（2D 双栏对照）与「模块空间」（3D 三舱一塔三桥）本质是同一对象的两种视图，却各占一个模式位；加上「模板空间」又是另一粒度，三个“空间”并列让用户分不清谁包含谁。

模块(2D 双栏) vs 模块空间(3D 三舱) = 同对象不同视图；模板空间 = 更细粒度

✕知识轴与资产轴混排

「结果库」「模板与技术」是数据产线资产 / 证据档案（生产轴），而「图谱全景」「跨线账本」是机制知识（知识轴），四者平铺在同一 tab 行，认知负荷大。

[知识] 全景 + 账本　⟷　[资产] 结果库 + 模板技术 ← 两类目标混在一行

✕命名漂移 & 死件残留

「模板与技术」曾叫「注册表」；「图谱」既作 tab 名又作全景内部标题；`lens=atlas` 是 URL 兼容别名，与「路线」导航重复。多处历史命名随版本迭代漂移，新老概念并存。

注册表→模板与技术 / 图谱(tab) ≡ 图谱全景(内部) / ?lens=atlas 别名路由

02重构的三条设计原则

PRINCIPLE 1

一条主线：逆向研发流水线

界面顺序应还原平台的真实工作流——先看图谱里发现了什么，再看这些发现如何被账本验证，接着看用什么模板/技术生产证据，最后看分布式平台如何运行。导航即流程。

PRINCIPLE 2

对象 / 视图分离

“模块”“模板”是对象（研究对象），“2D 双栏”“3D 空间”“卡片”是视图（看的方式）。二者不能并列——视图应作为对象的子级切换，而不是平级 tab。

PRINCIPLE 3

知识 / 资产 / 运行 分域

区分三类信息：机制知识（特征/账本）、生产资产（模板/技术/研究包）、平台运行（节点/队列/租约）。同一屏最多呈现一类主线，避免混杂。

06落地路线（分三阶段，每阶段可独立验收）

P1 · 低风险取消二级 tab，改四域切换器

在 AtlasLens 内把「图谱全景/跨线账本/结果库/模板与技术」四个 tab 重新组织为「图谱全景 / 跨线账本 / 生产资产（合并结果库+模板技术）/ 平台运行（入口卡）」四个域；将「模块/模块空间/模板空间/卡片」从模式位降为「视图切换器」。

改动面：AtlasLens.jsx 主框架 + CSS；零后端改动；无数据迁移。

P2 · 语义归一对象/视图分离 + 命名收敛

确立“对象=特征/模块/模板，视图=全景图/2D/3D/卡片”的统一词汇表；消除「注册表→模板与技术」等历史命名；?lens=atlas 别名路由与「路线→图谱」导航语义统一（保留 URL 兼容，不再暴露为第二入口）。

改动面：LensProgress.jsx + 各视图组件标题/提示文案；同步更新设计文档词汇表。

P3 · 长期专项视图协议化收敛 + 平台运行深度联动

10 个 /rdc-* 独立页逐页协议化并入四域，删除独立路由；“平台运行”域从“入口卡”升级为与研发透镜共享同一状态源的实时视图（节点/队列/租约），实现分布式平台“一屏看全流程”。

改动面：涉及后端协议与多组件；需逐页回归，风险较高，独立排期。

07关键洞察：这不是“排版问题”，是“研究平台心智模型”问题

图谱界面的本质角色

在「分布式 LLM 逆向研发平台」里，图谱界面不是“一个功能页”，而是平台的知识中枢——它要回答三个问题：我们逆向出了什么（发现）？这些发现是否站得住（验证）？用什么资产持续生产证据（生产）？当前界面把这三个问题混在四个平级 tab 里，用户的心智模型被迫自己拼装。

“视图”是最大冗余来源

模块/模块空间/模板空间/卡片，本质是同一批研究对象的不同可视化方式。把它们并列，等于把“放大镜/显微镜/望远镜”当成了三种“研究对象”。正确做法是：对象固定，视图切换——这也是 v5 四透镜“对象路由即状态”原则在图形内部的自然延伸。
